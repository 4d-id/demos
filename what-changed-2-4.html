What changed in 2.4

SpecificationRelease notes

Revision 2.4 of the 4D-ID working draft is a specification change, not a product launch. It tightens five things that earlier drafts left loose: what an identifier is allowed to reveal, how far a reconciliation may reach, how an entity relates to the structures it sits inside, who may decide a contested merge, and which encoding implementers should use. This note describes what the draft now defines. Where the code does not yet do it, that is said plainly.

Defined is not the same as implemented

It is easy for a specification project to blur two very different statements. "The draft defines X" means a reader can implement X and know what correct behavior looks like. "The implementation does X" means you can run it. Those are separate claims with separate evidence, and conflating them is the most common way a standards effort loses the trust of the people it needs most.

So, the honest status line for this revision: the published schemas currently have 15 schema checks implemented of 112 defined; functional conformance work continues. The conformance suite enumerates 112 checks because the draft defines 112 testable behaviors. Fifteen of them have executable checks today, and those fifteen are schema level: they validate the shape of records, not the runtime behavior of a resolver. The remaining checks are written down as requirements, not as passing tests.

The reference resolver deployed behind this site reports version 2.4. That means it serves the 2.4 record shapes and the read-only routes documented on the home page. It does not mean every behavior described below is live in it.

Every number and status word should be true of the code as deployed. When in doubt, understate.

1. Genesis privacy: an identifier should not be a location disclosure

Earlier drafts had one identifier form, and it carried a discrete global grid cell in the string itself:

4did:h3:8c2a100d2d0dbff:c3BhdGlhbCBzYW1wbGUgYQ:20260412T094500Z
       ↑ genesis cell                             ↑ genesis marker

That form was never intended to say where a thing is now. The cell records where the entity was first grounded, and it is immutable for the life of the identifier, which makes it useful for routing and partitioning and useless as a position. The problem is social, not technical: a string that contains a grid cell gets read as a location by anyone who sees it, including in log files, support tickets, URLs, and screenshots. For a parked vehicle, a person's assistive device, or a sensitive facility, publishing the genesis cell is a disclosure nobody consented to.

Revision 2.4 defines a second identifier form that carries no spatial component:

4did:id:5a89fc81f07739510a815e8c202160ac:7KQ2P4M9XRB6TJ0VN3YH8D
        ↑ home token   ↑ local identifier

The home token names the resolver domain responsible for the identifier, so the string still routes. The spatial anchor moves out of the identifier and becomes a registration on the entity record, where it can be access-controlled, superseded, or withheld like any other attribute. Both forms remain valid. The draft states that producers handling entities whose first-grounding location is sensitive should prefer the non-spatial form, and that consumers must not treat either form's structure as a statement about current position.

Why this is a draft change and not a migration

Existing identifiers stay valid

Nothing about the spatial form is deprecated, and no identifier needs to be rewritten. Rewriting identifiers would defeat their purpose. The draft adds a form, states when to prefer it, and makes both forms resolvable by the same routes.

2. Reconciliation with bounds

Earlier drafts described merge and split without saying how far a reconciliation chain may reach. In practice that invites two failure modes. A resolver can follow redirects forever when records are cyclic or corrupt, and a merge proposal can be applied transitively across a graph until unrelated entities are collapsed into each other.

2.4 defines bounds for both. A resolver MUST stop following a merge chain after a defined hop limit and return the last reachable record with an explicit truncation flag, rather than failing silently or looping. A merge candidate applies to exactly the two entities named in it; it does not propagate to their aliases, children, or representations. Anything wider requires its own candidate with its own evidence and its own authorized decision.

The reconciliation demo on this site has always followed a hop limit in its browser-side logic, which is why it was the easiest place to see the behavior. The draft now specifies it so independent implementations agree.

3. One parent, many registrations

This is the revision most likely to change how people model their data, and it comes from a real ambiguity. A loading dock sits inside a building. It also sits inside a fire district, a maintenance zone, a leasehold, a grid cell, and a customs area. Earlier drafts had a single containment relation, so modelers had to choose one true parent and then express everything else awkwardly, or allow multiple parents and accept that "the parent" stopped meaning anything.

2.4 separates the two ideas:

  • One parent. An entity has at most one parent, and it means physical-structural containment: the thing you would have to take apart to separate them. A room's parent is a floor. A sprinkler head's parent is a room. This keeps hierarchy a tree, which is what makes change locality and pose composition work.
  • Many registrations. Every other "is inside" relationship is a registration: a typed, time-bounded, independently authored statement that an entity falls within some zone, district, cell, or administrative area. Registrations may overlap, may come from different authorities, and may expire. Nothing about them has to form a tree.

The practical effect is a cleaner separation. The state still carries one current anchor and one pose relative to the composition parent. It may also carry many external registrations to BIM, scan, survey, device-map, or other frames, each with its own validity, tier, confidence, status, and provenance. None of those registrations adds a parent or establishes identity. That is also why the genesis cell in the spatial identifier form, the current anchor, and external registrations must not be read as one field.

4. Governance clause 14.4

A shared identity layer has a question it cannot avoid: when two parties disagree about whether a merge should stand, what happens? Earlier drafts said merges require authority without saying what an authority is or what a dispute does.

Clause 14.4 defines scoped grants, overlapping authority claims, and dispute records. A dispute identifies the claim or decision, the raising principal, evidence, review authority, scope, limits, expiry, and status. Filing a dispute does not automatically merge, split, transfer, terminate, or overwrite state. A separately authenticated and authorized operation enacts any disposition, while prior decisions and unresolved conflicts remain available under the declared retention and disclosure policies.

The design rule behind it: identity history is append-only, and disagreement is data. A record of "these two were merged, then contested, then split again by this authority at this time" is more useful to a downstream system than a record that quietly shows one outcome.

5. One encoding, pointed at rather than invented

Revision 2.4 adds a versioned encoding document that points to the JSON Schema 2020-12 record bindings, the informative OpenAPI 3.1 surface, RFC 9562 UUID descriptors, and the exact limits of those artifacts. It also states what the schemas cannot prove, including entropy, identity truth, authority, interval ordering, and functional conformance. A consumer that parses referent meaning out of the local descriptor is relying on something the draft does not promise.

What you can actually run today

Implementation status, stated at the level of evidence rather than intention:

  • Record shapes for both identifier forms: defined in the draft and covered by the schema checks that exist.
  • Read-only resolution routes: running on the reference resolver at version 2.4.
  • Reconciliation bounds, contested merges, parent and registration separation: defined in the draft. Partially present in the reference resolver and in the browser-side demos on this site, which are illustrative sandboxes rather than conformance evidence.
  • Functional conformance: 15 schema checks implemented of 112 defined; functional conformance work continues. There is no certification program, and no claim that any implementation passes the full suite.

The identity inspector on this site parses both identifier forms and shows, for any identifier you paste in, what the syntax tells you and what only a resolver could tell you. It was built for this revision because the distinction between those two things is the whole point of the genesis-privacy change.

Open for 2.5

One question is deliberately unresolved and worth naming, because it is the kind of thing that is cheap to change now and expensive later: whether a zone should be allowed one grid system or several, and relatedly whether the genesis marker in the spatial identifier form should carry the cell at all, or whether the cell should live only as a registration. 2.4 makes the second option possible by adding the non-spatial form. It does not yet make it the recommendation.

The draft, the conformance suite, and the reference resolver are open. 4D-ID is a working draft offered for community review, and this revision is a better argument than the last one mostly because more of it is written down as testable behavior. The conformance CLI is the honest place to check any claim made here.

Keep exploring.
